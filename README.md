# Taiwan Stock Industry Radar

An investment **research and decision-support** dashboard for Taiwan-listed equities. It tracks capital rotation, strengthening industries, and leading indicators — the upstream data that tends to move before share prices do.

> **This is not a trading signal generator.** No page issues a buy or sell instruction, and nothing here promises returns. Stocks and industries are labelled by *cycle position* (Early Strengthening, Trend Confirmed, Overheated, …), never bullish/bearish.

> **Prices, flows, fundamentals and catalysts are real; most leading indicators are not.** In the default live mode every price, volume, institutional net-buy figure, monthly revenue and catalyst comes from an official TWSE / TPEx / MOPS report. Of the 49 leading indicators, only two have a free authoritative source and are wired; the rest are licensed data and stay empty until imported. Every row carries `isMock` and a `DataSource`, so provenance is queryable per row. See [Data sources](#data-sources) and [Indicator coverage](#indicator-coverage).

> **`DATA_MODE=mock` restores the original synthetic dataset**, where every number is generated by a seeded PRNG. Useful offline and for UI work; never mixed with live data.

## Quick start

```bash
npm install

# A Postgres to point at. Any instance works; this is the throwaway one.
docker run --name radar-pg -e POSTGRES_PASSWORD=postgres   -e POSTGRES_DB=radar -p 5432:5432 -d postgres:17
cp .env.example .env        # then set DATABASE_URL + DATABASE_URL_UNPOOLED

npx prisma migrate dev      # applies migrations
npm run verify:sources      # ~1 min: confirms every live feed still parses
npm run db:seed:live        # seeds the taxonomy only — no numbers
npm run db:backfill         # real history; re-run until "remaining: 0"
npm run jobs:daily          # refresh → scores → alerts → AI brief
npm run dev                 # http://localhost:3000
```

`npm run db:bootstrap` runs migrate → taxonomy → backfill → daily in one command.

**The backfill is not optional.** Relative strength looks back 60 sessions, the
volume-expansion reading needs a 20-session baseline, revenue is compared
year-over-year, and the sentiment ranking needs five prior sessions before
`#9 → #1 ↑8` means anything. A live daily job alone leaves every one of those
computing against a one-row window.

### The backfill expects to be interrupted

`www.twse.com.tw` enforces a rolling request quota per client across the
**whole host** — not per report path. Exceed it and every endpoint on that host
returns a 307 "for security reasons" page, including ones you have barely
touched; it clears on its own within minutes. There is no paid tier, no key,
and no bulk endpoint to ask for instead. `openapi.twse.com.tw` is the sanctioned
API and is never throttled, but it only ever serves the current month.

Two consequences shape the whole design:

**The backfill is a resumable collector, not a one-shot job.** Each run takes a
request budget (`--max-requests`, default 140), writes as it goes, and stops
cleanly when the budget is spent. Every leg checks what is already stored and
skips it, and a block or spent budget ends only that leg — the next may target
a different, unthrottled host. Run it repeatedly until it reports
`remaining units of work: ~0`. Spacing runs an hour apart works better than
raising the budget, because the quota refills on time.

**History is seeded from FinMind, then converged to official data.** The
exchanges publish per-session reports, so one stock over five months costs six
requests and 55 stocks cost 330 — against that quota. FinMind is organised the
other way round: one request returns a whole date range, so the same history
costs 55 requests. So `seed-prices` / `seed-flows` make the app usable within
minutes, and the official `prices` / `flows` legs then overwrite those rows in
place as quota allows. This works because every write is an upsert on
`(entity, date)` that also rewrites `dataSourceId`, and because coverage is
tracked **per source** — see `loadPriceCoverage(sourceKey)`. Counting any row as
covered would make the official catch-up a silent no-op forever.

Individual legs can be run alone with `--only=prices`, and
`--status-detail=0` skips the breadth/market-flow history, which is the most
expensive leg per unit of value (three requests per session for fields no page
reads historically).

Both seed scripts start by clearing every table, and `WatchlistItem` is the
only one holding data a person authored rather than data a feed produced. Save
it across a re-seed:

```bash
npm run watchlist:backup  -- data/watchlist-backup.json
npm run db:seed:live
npm run watchlist:restore -- data/watchlist-backup.json
```

Items are keyed by industry slug / ticker / indicator key rather than by cuid,
since a re-seed issues fresh ids.

### Demo mode

```bash
DATA_MODE=mock              # in .env
```

## Decision flow

The navigation follows the intended research path:

**Overview → Industry Momentum → Industry Radar → Capital Flow → Stocks → Leading Indicators**

The homepage is a **digest, not a workspace**. It answers five questions with the top five rows of each, and every block links to the screen that owns the full dataset:

| Question | Block | Full screen |
| --- | --- | --- |
| Which groups are moving **today**, whole-group? (產業氣氛) | 短線氣氛 TOP 5 | `/momentum` |
| Which industries are improving over the medium term? (產業熱度) | 產業熱度 TOP 5 | `/industries` |
| Where is money flowing now? | 資金流向 (top 3 in / out) | `/capital-flow` |
| Which names moved? | 個股焦點 TOP 5 | `/stocks` |
| Which indicators changed before prices? | 領先指標異動 (top 4) | `/indicators` |

The first two are deliberately adjacent: an industry can be rising on money that only one or two of its names are absorbing, and only the breadth reading separates that from a genuine group move.

### Layout

Every section is a **card** — a bordered, rounded box with its own header, body and footer link — rather than a band separated by a horizontal rule. A rule divides sections on a wide sheet; on a phone every band is the same width and the rules stop dividing anything, so the box is the unit of layout. Type-level elements (status chips, filter chips, score bars, KPI numerals) stay at radius 0, which is the Modernist system's signature; only containers round. See `.rd-card*` / `.rd-tap` in `src/app/globals.css` and `src/components/radar/panel.tsx`.

Dense tables (產業氣氛, 個股雷達) render **twice**: the multi-column grid from `lg` up, and one card per row below it. Their columns carry meaning by position and cannot reflow — compressing ten of them into 390px clipped industry names to a single character. `/capital-flow`'s heat map keeps its columns and scrolls horizontally instead, with an on-screen hint that it does.

## Industry Heat Score

A 0–100 composite of five separately-stored components:

| Component | Default weight | Derived from |
| --- | --- | --- |
| Fundamental momentum | 30% | Average revenue YoY across member stocks |
| Leading indicators | 25% | Per-period, direction-adjusted momentum of the industry's indicators |
| Capital flow | 20% | Foreign + trust net buying, normalized across industries that day |
| Technical strength | 15% | Trend participation + relative strength vs. TAIEX |
| News / catalyst | 10% | Recency- and importance-weighted catalysts |

Three properties are deliberate:

**Weights are configurable, never hard-coded in the UI.** They live in the `ScoreWeightConfig` table and are readable/writable at `/api/score-weights`. Each `IndustryScore` row also stores a `weightsSnapshot`, so a score computed last month stays reproducible after the weighting changes.

**One derivation, used everywhere.** `src/lib/jobs/compute-scores.ts` is the single source of truth. Both the historical backfill and the daily refresh call it, so the week-over-week deltas the UI shows measure changing market conditions rather than a change of formula. (An earlier version generated seed history with one formula and today's score with another — every industry then read "Weakening" from a pure artifact.)

**Components are squashed, not clamped.** Each raw signal passes through `50 + 50·tanh(x/scale)`. A linear map pins to 0 or 100 as soon as a signal is moderately strong, which collapses the scale to its extremes and makes industries indistinguishable. The same applies to relative strength: a hard clamp ties every strong name at the ceiling, destroying the ranking exactly where it matters most.

Everything is computed strictly **as of** a given date — no row dated later can influence it. That is what makes indicator-vs-subsequent-price backtesting possible later.

## Industry Sentiment Score

A second, deliberately **separate** 0–100 score. Heat asks *"is this a good industry to own over the coming weeks"*; sentiment asks *"is this industry strengthening today, and is the whole group participating"*. They routinely disagree, which is the point of showing both — the two never share a table, a weight config, or a status vocabulary.

| Component | Default weight | Derived from |
| --- | --- | --- |
| Advancing stock ratio | 25% | Share of member stocks up today (8 of 10 up → 80) |
| Average industry return | 20% | Equal-weighted average member return |
| Volume expansion | 15% | Session turnover ÷ trailing 20-session average turnover |
| Breakout stock ratio | 15% | Share of members in a technical breakout |
| Institutional flow | 15% | Foreign + trust + ½ dealer net, over the group's own turnover |
| Relative strength vs. TAIEX | 10% | Today's spread blended with the trailing 5-session spread |

Weights live in `SentimentWeightConfig` and are readable/writable at `/api/sentiment-weights`. Every snapshot stores its own `weightsSnapshot`, so history stays reproducible after a retune. `src/lib/sentiment.ts` is the only place the formula exists — UI components never re-derive a component score or hard-code a weight.

**Breadth is the point.** `Industry +5%, ten names rising` and `Industry +5%, one limit-up and nine flat` must not score the same. The advancing ratio, breakout ratio, and the breadth bar (上漲 / 平盤 / 下跌) exist to separate them; the score's largest single weight is on breadth for that reason.

**Change is ranked above level.** Every session is stored as an `IndustrySentimentSnapshot` with `rank`, `previousRank`, `rank5dAgo`, and `rankDelta`, so the UI leads with `#9 → #1 ↑8` rather than a static ranking. The status classifier checks acceleration and deterioration before it describes the level.

**Normalization is per-component, and the shape is deliberate.** Ratios that are already a share of the group (advancing, breakout) map linearly, because "8 of 10 up = 80" is the number a reader wants to see. Unbounded signals (return, volume, flow, relative strength) are squashed with `50 + 50·tanh(x/scale)` for the same reason the heat score does it. Institutional flow is normalized by the group's *own* turnover rather than cross-sectionally, so a quiet industry's score does not move when some unrelated industry prints a large block.

Statuses:

| Status | Fires when |
| --- | --- |
| 短線過熱 | Score ≥ 78 **and** average return ≥ 3% or volume ≥ 2.0× — checked first, so the caution is never masked. **Not** a bearish label |
| 加速轉強 | Score ≥ 55 **and** score up ≥ 10 or rank up ≥ 5 vs. the previous session |
| 強勢群聚 | Score ≥ 70, ≥ 70% of members up, and beating TAIEX |
| 弱勢群聚 | Score ≤ 30, ≤ 30% of members up, and lagging TAIEX |
| 轉弱 | Score down ≥ 10 or rank down ≥ 5 |
| 多方 / 中性偏多 / 中性 / 中性偏空 | Level description, once nothing is changing sharply |

**Breakout detection is modular.** `src/lib/breakout.ts` holds independent predicates over one price series — close above the prior 20-session high, and a break of a tight 20-session consolidation. Volume expansion is recorded as *confirmation* and cannot qualify a stock on its own, so a quiet breakout still counts toward breadth. Tightening or extending the definition means adding an entry to `DEFAULT_BREAKOUT_RULES`; no caller, score, or component changes.

**細產業 (sub-industry).** `Stock.subIndustry` carries a finer classification inside each industry (ABF 載板 inside PCB, 液冷模組 inside 散熱). Sub-groups are scored with the identical formula but are **not** persisted — spec-level history is defined at industry level, and sub-groups are cheap to recompute from the price series already loaded. Their day-over-day rank change is derived by running the same computation for the previous session. Their institutional flow sums real per-stock prints where those exist; where they don't, the parent industry's flow is apportioned by turnover share and flagged `推估` in the UI, never presented as a measured print.

**Sentiment vs. Heat.** Both scores are shown side by side on the industry detail page, labelled with the quadrant they land in:

| | High heat | Low heat |
| --- | --- | --- |
| **High sentiment** | 主流趨勢 — move has fundamental support | 題材急拉 — short-term participation running ahead of the slower signals |
| **Low sentiment** | 高檔休息 — medium-term score intact, short-term cooled | 低度關注 |

No buy/sell signal is generated from any of this.

## Analytical separation

Fundamental quality and short-term price strength are kept apart, per the design principle that a strong business already priced for perfection reads differently from a strong business the market hasn't caught up to.

Stock statuses:

| Status | Meaning |
| --- | --- |
| Early Strengthening | Turning up; move not yet widely recognized |
| Trend Confirmed | Breakout with relative strength confirming |
| Potential Catch-Up | Fundamentals improving but price still lagging peers |
| High-Level Consolidation | Holding gains without new highs |
| Overheated | Stretched above its own trend, not merely near its highs |
| Weakening | Breaking down or lagging the market |

The Overheated test uses `extensionPct` (close vs. its own 20-session mean) rather than range position alone — an established uptrend sits near its highs by construction, so range position cannot separate a healthy advance from a parabolic one.

## Alert engine

Rule-based, idempotent per calendar day + rule + industry, so re-running is safe.

| Rule | Fires when |
| --- | --- |
| `indicator_consecutive_rise:<key>` | A bullish-direction indicator rises 2+ consecutive readings |
| `indicator_spike:<key>` | Any indicator moves more than 5% in one period |
| `foreign_buy_streak` | Foreign investors net-buy an industry 3+ consecutive sessions |
| `turnover_spike` | Industry turnover exceeds 1.6× its trailing average |
| `breakout_cluster` | 3+ stocks in one industry break above consolidation together |
| `relative_strength_new_high` | Industry relative strength reaches 115+ |

Every alert carries a timestamp, industry, source indicator, observed change, importance, related stocks, and a plain-language explanation of *why the rule matters*.

A streak that fills the whole query window is reported as `N+` rather than claiming an exact count the data cannot support.

## Daily AI brief

`/daily-brief` renders 11 sections plus a three-way epistemic split the AI layer is required to maintain. Section 02 (短線產業氣氛) reports 氣氛值上升最快族群 / 下降最快族群 / 排名躍升最多族群 / 強勢群聚族群 / 短線過熱族群, and the prompt requires the model to keep the short-term sentiment score and the medium-term heat score distinct rather than averaging them.

- **Known Facts** — directly observed from the data
- **Reasonable Inference** — interpretation across multiple indicators, labelled as inference
- **Uncertainty / Risk** — what could invalidate the thesis, and the data's limitations

Providers are pluggable via `AI_PROVIDER`:

| Value | Behaviour |
| --- | --- |
| `mock` (default) | Rule-based composition, no API key needed. Always populated. |
| `openai` | `POST /v1/chat/completions` with JSON mode |
| `claude` | `POST /v1/messages` |

Real providers fall back to `mock` on any failure (missing key, network error, malformed response), so the page never breaks. The system prompt constrains the model to the numeric facts supplied in context, forbids invented figures, forbids buy/sell instructions, and forbids promising returns.

**Collectors are decoupled from the frontend.** Every data source implements an interface in `src/lib/providers/types.ts`:

```ts
interface IndicatorProvider {
  source: ProviderSource;              // key, name, category, url, isMock
  fetchLatest(): Promise<IndicatorResult[]>;
}
```

Nothing above the provider layer knows whether a value came from an official feed or a synthetic generator — the provider declares its own provenance and the refresh job stamps it onto every row. To move collection into a Python or Spring Boot service later, have it write to the same tables (or expose the same shapes) — the pages, scoring, and alerting are untouched.

**Write helpers are shared between the daily job and the backfill.** `src/lib/jobs/persist.ts` holds every write, so a backfilled session and a freshly pulled one differ only in when they were fetched. Any divergence in units, provenance or derived fields would otherwise show up as a phantom regime change on the exact date the two meet.

**View models sit between Prisma and the UI.** Pages consume the shapes in `src/lib/queries.ts`, not raw Prisma rows, so storage can change without rewriting components.

**Data provenance is first-class.** Every `IndicatorValue`, `MarketData`, `InstitutionalFlow`, `StockFundamental`, `Catalyst` and `MarketStatus` row links to a `DataSource` and carries `isMock`, and indicator values additionally carry `dataTimestamp` and `sourceUrl`. The view models in `queries.ts` pass `isMock` through, but **no component renders it yet** — surfacing provenance in the UI is still open.

### One caveat on the demo dataset (`DATA_MODE=mock`)

The synthetic seed deliberately models **correlation**, not just plausible-looking noise:

- Stocks in one industry share a per-session "attention factor", so a whole group trades heavier and moves together on the same days. Generated independently, several stocks in one industry expanding volume on the same session is statistically near-impossible — and the group-strength detector would never have anything real to find.
- Institutional flow is *derived* from the price and volume action (direction follows the move, conviction follows volume). Independent noise routinely claimed institutions accumulated a group that fell, which contradicts the premise the product rests on.

## Jobs and scheduling

```bash
npm run jobs:refresh   # pull providers → recompute technicals, statuses, scores
npm run jobs:alerts    # evaluate alert rules
npm run jobs:brief     # generate the AI daily brief
npm run jobs:daily     # all three, in order
npm run cron           # long-running scheduler, 20:00 Asia/Taipei, Mon–Fri
```

```bash
npm run verify:sources # read-only: confirm every live feed still parses
```

On serverless platforms use the platform scheduler against the job routes instead of `npm run cron`. Set `CRON_SECRET` and send it as `Authorization: Bearer <secret>`. With no secret configured the job routes are allowed only outside production, so a deployed instance can never be triggered anonymously. Vercel Cron only sends `GET`, so every job route exports a `GET` alias, and Vercel sends `CRON_SECRET` as a bearer token automatically.

**`vercel.json` schedules the whole pipeline as one entry, plus a health check:**

| Time (UTC) | Route | What it does |
| --- | --- | --- |
| 12:00 | `/api/jobs/daily` | refresh → alerts → brief → revalidate, in that order, in one invocation |
| 16:00 | `/api/jobs/verify` | Read-only feed-shape check; returns 503 if any feed drifted |

The single entry is deliberate, and it is a plan constraint rather than a
preference. **Hobby cron precision is ±59 minutes**: an entry scheduled at
12:00 fires somewhere in 12:00–12:59. Two entries ten minutes apart therefore
have no guaranteed order, and `alerts` running before `refresh` does not fail —
it reads the previous session and emits confident, wrong alerts, then `brief`
narrates them. Sequencing the stages inside one function is the only ordering
guarantee this plan offers.

It fits: **the full pipeline measures 91 s against Hobby's 300 s ceiling**
(refresh 84 s of it — see `RefreshSummary.timings` for the per-step split,
which is spread evenly across nine steps with no single hot spot). Every write
is an upsert, so a run killed partway is repaired by the next day's.

The 4-hour gap before `verify` is sized to absorb the ±59 min jitter on *both*
entries — worst case the daily job starts at 12:59 and `verify` at 16:00 — so
`verify` can never observe a pre-job state and report a stale session as a
broken feed.

`/api/jobs/verify` is the one worth scheduling forever. These are public
reports, not versioned APIs: a renamed column produces a plausible-looking
wrong number rather than an error, and this project has already shipped one
(market turnover read from 成交股數 instead of 成交金額, rendering as a
perfectly believable "88 億"). It writes nothing and returns 503 on any failed
check, so a scheduler surfaces drift as a failed invocation.

## Database

PostgreSQL, via Prisma. The datasource declares two URLs:

| Variable | Used by | Must be |
| --- | --- | --- |
| `DATABASE_URL` | the running app | pooled, if a pooler exists |
| `DATABASE_URL_UNPOOLED` | `prisma migrate` (`directUrl`) | a direct connection |

Migrations run through a transaction pooler hang, which is why `directUrl` is
separate. Without a pooler in front of the database, set both to the same string.

Two schema notes worth knowing:

- Date-keyed rows use a **UTC** midnight boundary via `src/lib/dates.ts`. Using the runtime's local midnight produces a different key per timezone and silently duplicates rows.
- `WatchlistItem` has no compound unique constraint. Its natural key spans nullable columns, and both SQLite and Postgres treat NULLs in a unique index as distinct — the constraint would never fire. Uniqueness is enforced in `src/app/watchlist/actions.ts`.

## Deploying to Vercel

1. **Import the repo** at vercel.com. Do not deploy yet — the generated Prisma
   client is gitignored, so `npm run build` runs `prisma generate` first, and
   that reads the schema, which fails until both database URLs exist.
2. **Create the database**: project → *Storage* → *Neon*. The integration
   injects `DATABASE_URL` and `DATABASE_URL_UNPOOLED` into every environment,
   which is exactly the pair the schema expects. Nothing to copy by hand.
3. **Set the remaining env vars** under *Settings → Environment Variables*:
   `CRON_SECRET` (any random string — Vercel sends it as
   `Authorization: Bearer <value>` on cron invocations), plus `AI_PROVIDER` and
   the matching API key if the brief should call a real model.
4. **Deploy.**
5. **Migrate and seed once.** Nothing here reads `dotenv` explicitly — the
   scripts inherit whatever Prisma Client loads from `.env` — so the simplest
   path is to swap the local `.env` for the production one:

   ```bash
   mv .env .env.local.bak
   ```

## Data sources

Every live provider lives in `src/lib/providers/live/` and is wired in `registry.ts`. All of these are free, public, and official — no API key, no scraping of a third-party aggregator.

| Data | Source | Endpoint |
| --- | --- | --- |
| Daily OHLCV, listed | TWSE 每日收盤行情 | `openapi.twse.com.tw/v1/exchangeReport/STOCK_DAY_ALL` (today), `rwd/zh/afterTrading/STOCK_DAY` (history) |
| Daily OHLCV, OTC | TPEx 上櫃日收盤行情 | `tpex.org.tw/openapi/v1/tpex_mainboard_daily_close_quotes`, `www/zh-tw/afterTrading/tradingStock` |
| TAIEX close / turnover | TWSE 市場成交資訊 | `rwd/zh/afterTrading/FMTQIK` |
| Advance / decline breadth | TWSE 大盤統計資訊 | `rwd/zh/afterTrading/MI_INDEX` |
| Market institutional net | TWSE 三大法人買賣金額 | `rwd/zh/fund/BFI82U` |
| Per-stock institutional net | TWSE T86 / TPEx 三大法人買賣明細 | `rwd/zh/fund/T86`, `www/zh-tw/insti/dailyTrade` |
| Margin financing balance | TWSE / TPEx 融資融券餘額 | `rwd/zh/marginTrading/MI_MARGN`, `www/zh-tw/margin/balance` |
| Monthly revenue | MOPS 每月營業收入彙總表 | `opendata/t187ap05_L`, `mopsfin_t187ap05_O` (current); `mopsov.twse.com.tw/nas/t21/{sii,otc}/t21sc03_*.html` (history, Big5) |
| Quarterly EPS | MOPS 各產業EPS統計 | `opendata/t187ap14_L`, `mopsfin_t187ap14_O` |
| Catalysts | MOPS 每日重大訊息 | `opendata/t187ap04_L`, `mopsfin_t187ap04_O` |
| Hyperscaler capex | SEC XBRL company facts | `data.sec.gov/api/xbrl/companyconcept` (MSFT, GOOGL, AMZN, META) |
| Historical prices / flows (seed only) | FinMind | `api.finmindtrade.com/api/v4/data` — see below |

**FinMind is the one third-party source, and only for seeding history.** It
aggregates the same public TWSE/TPEx filings rather than measuring anything
independently, so its values agree with the exchange — the 122 sessions it
returned matched the 122 the official `FMTQIK` report gave. It still gets its
own `DataSource` row: someone asking where a number came from deserves
"FinMind", not a claim it came from TWSE directly. Ongoing collection never
uses it.

Three further properties of the wiring are deliberate:

**Industry and market flow are derived, never separately fetched.** The exchanges publish institutional trading per stock; the industry figure is the sum of its members and the market figure comes from the same row that populates the market-status header. Fetching each scope independently is how an industry card ends up disagreeing with the stock list underneath it.

**Per-stock flows are valued at the session close.** Neither exchange publishes stock-level institutional trading in currency — only in shares — so `foreignNet` is `net shares × close ÷ 1000`. That is an approximation of true traded value and the conventional one; it is also the only way the stock, industry and market scopes can share a unit. Providers declare `unit: "shares"` and the conversion happens once, in `writeStockFlows`.

**Indicator values are dated by publication, not by period.** A Q1 capex figure is stored against the filing date, and a monthly revenue aggregate against the 10th of the following month. Dating them to the period they describe would let a score computed in April read a number nobody could see until May — the lookahead bias that makes indicator-vs-price backtesting lie.

### Indicator coverage

Of 49 leading indicators, 2 are live:

| Indicator | Source |
| --- | --- |
| `hyperscaler_capex` | SEC XBRL — aggregate quarterly capex of MSFT + GOOGL + AMZN + META, from the filings themselves |
| `odm_monthly_revenue` | Derived from the stored MOPS revenue of the AI-server ODM constituents |

The other 47 are licensed data with no lawful free endpoint — SCFI and Drewry WCI (freight), TrendForce (DRAM/NAND/panel pricing), SEMI (WFE billings, wafer shipment area), and the utilization / book-to-bill / inventory-week series that only appear in paid research. They are **not** approximated by a proxy: substituting AMAT+LRCX+KLA revenue for "WFE billings", say, would quietly change what the indicator measures while the UI kept the original label and unit.

Load them from whatever you have access to:

```bash
npm run import:indicators -- data/indicators.csv
```

```csv
indicator_key,date,value,source_url
scfi,2026-08-22,1842.5,https://en.sse.net.cn/indices/scfinew.jsp
dram_contract_price,2026-08-01,2.15,https://www.trendforce.com/
```

`date` is when the value was published or became effective, for the same lookahead reason above. Imported rows land with `isMock: false` and are indistinguishable from feed-sourced values downstream, which is correct — they are equally real. Unknown indicator keys abort the import rather than being silently skipped.

Until an indicator has values, the leading-indicator component (25% of the heat score) contributes a neutral 50 for that industry rather than a number derived from nothing.

### Known gaps

- **`/alerts` has no page.** It is listed in the Pages table above but no route
  exists; alerts render on the homepage instead.
- **Provenance is not surfaced in the UI.** Every row carries `isMock` and a
  `DataSource`, and `queries.ts` passes `isMock` through, but no component
  renders it.
- **Market breadth and market-level flow only exist for recent sessions.** They
  cost three throttled requests per session, so `--status-detail` bounds them.
  On a session where they were never fetched the columns sit at their schema
  default of `0` — which for these fields is indistinguishable from a measured
  zero. Only the latest session is displayed, so this is a storage wart rather
  than a visible bug, but it is the one place the "never fabricate a reading"
  rule is defeated by the schema being non-nullable.
- **`APP_URL` must be set in production** or the daily job cannot invalidate the
  read cache, and the dashboard can serve pre-job data for up to a day. The job
  warns when it is missing.

### Adding a source

Implement the relevant interface from `src/lib/providers/types.ts`, declare a `ProviderSource` on the class, and add it to `registry.ts`. The refresh job upserts the `DataSource` row from that declaration and stamps every row it writes, so `isMock` always reflects the provider that actually produced the value. Keep each provider isolated: one broken feed should degrade one series, not the pipeline.

### Operational notes

- **Rate limits.** `src/lib/providers/live/http.ts` serializes requests per host with a minimum spacing (2.2 s for `www.twse.com.tw`, 1.2 s for TPEx, 0.4 s for the OpenAPI CDN) and retries 429/5xx with backoff. Do not parallelize around it.
- **Feed drift.** These are public reports, not versioned APIs. A column reorder would surface as plausible-looking wrong numbers, so `npm run verify:sources` asserts the shape of every feed without writing anything. Worth running in CI on a schedule.
- **Session dates, not wall-clock dates.** The pipeline computes for the latest *published* session. Taiwan closes at 13:30 and publishes through the evening, so a job keyed on "today" would write empty sessions every weekend and half-empty ones before publication.
- **Delisted tickers.** `2456` (奇力新) was merged into `2327` and no longer trades. The backfill resolves every ticker against the live listings and warns loudly rather than silently producing a stock with no history.
